## 2. REGRESSIONS — introduced by the rewrite

### R1. The stage floor divides by the wrong beat count (critical, M9, change 8)
`program/fws_build.py:475` lowers stage *s* for traversals `0 .. beats−s−1`, so stage *s* fires exactly `beats − s` times. `fws_eval.py:2278` divides every stage's union‑busy by `beats`.

Falcon‑Mamba is the proof. It is 32 identical Mamba stages. The shipped per‑stage compute column decays 8.063158e‑07 (s0) → 4.126218e‑07 (s31), a ratio of 1.9542 against `beats/(beats−31) = 65/34 = 1.9118`. Divide each row by its own firing count and s0, s1 and s2 all give 8.0631579e‑07 — identical to 8 significant figures. Identical stages cannot have a 1.95× spread in service time. The spread is the divisor.

The docstring at `fws_eval.py:2246` calls the quantity \"a RATE … so it does not move with the measurement window\". Measured on Granite: stage_floor 1.171816e‑05 → 1.178888e‑05 → 1.183786e‑05 → 1.192021e‑05 s at windows 20/25/30/40.

Corrected floors: Granite 1.2364882e‑05 s at **stage 17** (not stage 2 — a smaller divisor overtakes), which exceeds the Little floor and flips `beat_binding`. Granite 83190.9 → 80874.2 tok/s. Qwen 52546.9 → 49348.5. Falcon 534700.8 → 531177.5.

**Fix:** divide by `beats − stage`, or by the count of distinct `cost.step` values seen for that stage.

### R2. Only the largest hop per stage is charged (critical, M8, new with the stage‑occupancy rewrite)
`fws_eval.py:2261` diverts every `act.*` op out of the compute union. Line 2264 folds them into `link_s[stage] = max(...)`.

Granite stage 2 carries three distinct `act.*` boundary ids: `act.c1->c2` (1.0286102294921875e‑06 s), `act.L5.qkv_to_fabric` (1.0068119594029017e‑06 s, fired **7×** per beat), `act.L5.fabric_to_o_proj` (1.0286102294921875e‑06 s). Sum of the three distinct hops = 3.0640324e‑06 s. The report charges 1.0286102294921875e‑06 s. **2.0354222e‑06 s per beat is charged neither as compute nor as link.**

They are serial, not overlapping. The per‑traversal union of stage 2 including the `act.*` ops is 1.470298e‑05 s against 1.163895e‑05 s excluding them — a difference of 3.06403e‑06 s, equal to the sum of the three distinct hops to 6 digits.

1.470298e‑05 s is the max over all 20 stages. Granite 83190.9 → **68013.3 tok/s (−18.2%)**. Falcon moves 0% here; it is pure Mamba and has no intra‑stage hops. The comment at `fws_eval.py:2262` (\"ONE token crosses this link once per beat\") is also false — `qkv_to_fabric` fires 7× per beat. `link_s` carries two physical quantities under one name (M7).

**Fix:** put intra‑stage `act.*` hops back into the compute union. Sum, do not max, several distinct outgoing hops.

### R3. The softmax copy count saturates at `n`, not at the chunk count (critical, M2, change 5)
The law at `cim_timing.py:3384` is `chunks = rows * ceil(keys / softmax_width)`, then `per_copy = ceil(chunks / copies)`. `softmax_width` is `fabric.cols = 64`, a device constant. The searched quantity is **copies**. `AttentionCallDemand.saturation_softmax_width` (`cim_timing.py:2803`) returns `max(1, int(self.n))`.

Qwen: rows = 4 × 4 = 16, `ceil(1823/64) = 29`, chunks = **464**. Derived copies = **1823**. Re‑priced with the repo's own `_stage_attention_cycles` at arrays = 8: copies 463 → softmax 21 cycles; copies 464 → 20; copies 1823 → 20; copies 4000 → 20. **1359 excess copies.** Every stage takes the saturated branch (`target_kind = fold_concurrency_saturated_below_analog_time`), so the minimality search never runs.

Composed from the checked‑in 22 nm library: 1 copy = 0.418187081 mm² / 0.61214356 W. 1359 × 0.418187081 = 568.316 mm²/chiplet × 8 = **4546.530 mm²**. Qwen 15261.1 → 10714.6 mm² (−29.8%). Power 10430.461 → 3775.236 W (−63.8%). Granite: chunks 348 vs 1812 derived, 1464 excess × 5 chiplets = 3061.13 mm², 15923.4 → 12862.3 mm² (−19.2%). Softmax op energy falls 3.929× (Qwen) and 5.207× (Granite). **Throughput is bit‑identical at the saturating copy count on both.**

`derive_fabric_sizing`'s own docstring defines the saturation width as \"the smallest width past which no width helps\". That is 464, not 1823. This is an internal contradiction, so it is a defect and not an intended reading. `docs/qif/NUMBERS_AUDIT.md:240` already records this branch at the pre‑rewrite numbers (11.708 mm²/chiplet). Change 5 multiplied its cost by ~65×.

**Fix:** return `max(1, rows * ceil(n / softmax_width))`. Rename the field and `StageFabricSizing.softmax_width` to `softmax_copies`. Correct `cim_timing.py:4788`, which names a third bound (16 for Qwen).

### R4. QK and PV each pay the whole SA fabric (critical, M9, change 6)
`fws_eval.py:800` names engine `sa_fabric` for both `attention_qk` and `attention_pv`. Line 825 charges the full `sa_fabric_composition().power_w` = 14.7460071 W. The timing law splits the fabric: `fold_group_split` returns `a_qk + a_pv = num_arrays`, and both shipped runs report `qk_arrays = 4`, `pv_arrays = 4` of 8. The DAG serialises the three ops. While QK runs, the 4‑array PV group is idle.

Granite: QK 14.7460071 × 8.664821e‑04 = 1.277715e10 pJ; own group (8 GEMMINI + TRANSPOSER) 7.3785671 W → 6.393396e9. PV 7.413640e9 → 3.704023e9. Delta 1.0093372e10 pJ = **−23.24%** of the total. Qwen delta 5.3185981e10 = **−37.54%**.

The only disclosure on this term (`fws_eval.py:763`) names the gap in the **opposite** direction: \"an idle engine costs 0 pJ here, which is a floor, not a measurement.\" The code over‑charges. A named absence with the wrong sign does not cover this.

**Fix:** charge QK `ceil(r/32)*ceil(c/32)*a_qk` blocks plus the TRANSPOSER, and PV `…*a_pv` blocks. The split is already computed and already reported as `qk_arrays` / `pv_arrays`.

### R5. `_chip_boundary` severs the stage‑hold edge (critical, M9, change 7)
`program/fws_build.py:485` adds `held = stage_tail[(traversal−1, stage.index)]` to enforce D29's one‑stream‑per‑stage law. `_chip_boundary` selects the source‑chip producer and then `return [uid]` at line 669. Every other dep is dropped.

Instrumented on the shipped Granite lowering: 589 boundaries, 570 arrive with 2 deps (exactly 1 on the source chip), 19 with 1 dep (traversal 0). The held op lives on the **destination** chip, so it is always the discarded dep. The comment at line 640 records that the old code used `deps[-1]`, which **was** the held op — the hold edge survived, through a hop then priced at 0 s.

Measured overlap: stage 0 keeps its hold edge (no boundary is emitted when `previous_chip is None`) and gives 8.884211e‑07 s in both the per‑traversal and the union/firings column. Stage 5 gives 8.888889e‑07 vs 4.439181e‑07 (2.0×). Stage 19 gives 8.884211e‑07 vs 6.338756e‑07.

With correct per‑traversal service, Granite's binding stage 2 is 1.163895e‑05 + 1.028610e‑06 = 1.266756e‑05 s → 78942.6 tok/s (−5.1%, combined with R1).

**Fix:** `return [uid] + [d for d in deps if d != producer]`.

### R6. The handoff is charged to the destination stage (major, M7, changes 7/8)
`fws_eval.py:2246` and `:2263` both state \"each link charged to its source\". `transfer()` stamps `stage=self._stage` (`program/fws_build.py:393`) and `_rotation` sets `self._stage` to the **current** stage before the boundary out of the previous chip is emitted. Falcon: stage 0 becomes the max at 8.063158e‑07 + 1.076294e‑06 = 1.8826098e‑06 s, larger than the published 1.8702049e‑06 → 531177.5 tok/s (−0.66%). ### R8. MoE routed work grows as T² and is not monotone in the batch (major, M3, change 1)
