Plan P3

Mapping

Assign tiles to macros, macros to chips, and ops to devices — then hand the executor a placed, annotated op DAG.

Mission context

Mapping is the centerpiece. The QIF proposal calls it a compile-time placement problem; the rewrite already made placement a first-class policy; OPTIMA never had one. P3 is where the workload meets the machine.

Three stances bind this plan. A1: the output is a DAG, not a period law. A2: ops sit on typed devices — analog macro devices, per-macro digital pools, shared digital chiplets. A3: the macro is the atomic resource and the tile is the allocation unit, so mapping is the assignment of tiles to macros, macros to chips, and shards to groups.

Scope & exclusions

In: the mapping object and its relations; heterogeneous op placement; parallelism shard groups as annotations; config-declared allocation with validation and named violations; prefill/decode disaggregation (D16); per-boundary byte-rate checks.

Out: congestion, routing, buffering and topology — the network is fully-connected p2p with no congestion (D17, A1). Automatic mapping search — a later implementation behind a seam this plan fixes now (D10). Any bespoke area or cost objective (D19); P3 reports counts and rates, P4 owns metrics. Anything ported from OPTIMA's mapper or multi-tenant layer (D21).

The investigation

1. The mapping object

Four relations and one annotation set. Everything else is derived.

RelationFrom → toRuleInvariant
Residencytile → macro column setSpatial column allocation over cols × mux slots (A3, D10). Tiles from the same layer, other layers, other experts or other models may share a macro.Every occupied column set names an owner; capacity is never exceeded.
Assemblymacro → chipMany macros per chip. Chip ids are integers.No fractional chips (D21). Chip capacity checked, overflow is a hard error.
Packagechip → package graphFully-connected p2p, analytical (D17).Every cross-chip byte crosses exactly one link and is priced once.
Executionop → deviceExactly one device per op (A2).The device exists in the inventory and the op is priceable on it.
Annotationentity → (tp, ep, pp)Carried by every macro, chip and op.Constructed from (axis, coords), never inferred downstream.

Placement is logical only (D20): macro → chip and chip → package graph. No floorplan, no coordinates, no adjacency beyond the graph.

The owner of a macro is a tuple — tenant, model, layer, shard-group coordinate, tile index — and a macro carries a set of them. Named ownership is a D21 honesty invariant; ownership as a set rather than an exclusive claim is D22, and it is what makes multi-tenancy later a report rather than a rewrite.

The output of mapping is a placed, annotated op DAG: ops with explicit deps, explicit transfers, a device, a shard-group coordinate and an owner. It is never a closed-form period. Contention and occupancy emerge from the DAG plus resource assignment (A1). The closed-form spatial-pipeline report survives only as P6's validation reference.

One widening is needed and only one. DeviceCoord today addresses a homogeneous rank grid; here a device also has a class and a host macro. That is a wider coordinate, not a new IR.

5. The audit verdict: greenfield

AUDIT finding 1 is decisive. OPTIMA's _chip_accounting divides required area by usable chip area and in one mode reports non-integer chips. No layer is ever assigned to a chip; “layers/chip: 3” is division, not placement. There is nothing to port. OPTIMA contributes stage laws and single-model recordings to P2 and P6, and nothing to P3 (D21).

Two rules follow into our own artifacts, forever: chips are integers, and a relaxed constraint is disclosed in the artifact. Finding 5 is the anti-pattern — the flagship rows ran with max_link_bandwidth_GBs: 9999.

The seam, named now: one interface, (workload set, platform) → mapping. Config-declared allocation is the first implementation. The existing layers_per_chip: auto greedy packer is the second, already written. Automatic search is a third implementation of the same interface and a later phase (D10). The interface takes a set of workloads from day one; the singleton is a degenerate case, never a separate path.

7. Prefill and decode are two systems (D16)

 Prefill systemDecode system
Model instanceownown
Pool counts (macros, chips, shared chiplets)ownown
Mappingownown
Couplingone handoff, priced as bytes over the p2p law

That is the whole of it. No precision conversion — a seventh-order effect, out of scope. The only shared quantity is the handoff byte count. The report carries two system sections and one link line. Setting both specs equal reproduces the non-disaggregated machine.

8. Boundary bandwidth, checked honestly (D17, D21)

For each boundary — chip-to-chip activations, expert dispatch and combine, KV traffic, the PD handoff — mapping reports the required bytes per period against the declared link rate. A violation is named: boundary id, required rate, available rate, ratio. It is never silently absorbed and never fixed by raising a cap.

One honest limit, stated once and repeated in the artifact: with no congestion model, a violated boundary is reported, not priced. The DAG time in that case is optimistic and the report says so. If a run needs a relaxation to complete, the relaxation is disclosed.

Seams

Imports

  • P1 — the model set and per-model architecture facts: layer inventory, weight-matrix shapes, expert counts and routing, attention flavor, prefill/decode parameters, and the config-schema fields mapping consumes.
  • P2 — the macro resource model: device card, tile definition, stored-column capacity, bit-slice column sets, chained-macro reduction, per-macro pool sizing, occupancy semantics. Mapping asks P2 “does this tile set fit” and “what devices does this macro expose”.
  • P4 — the per-op pricing contract: which annotations an op must carry to be priceable, and the p2p law used for every boundary and the PD handoff.
  • P6 — the honesty invariants and the target-vs-provisional labelling every mapping report obeys.

Exports

  • The mapping object: tile→macro, macro→chip, chip→package, op→device, each with named owners.
  • A placed, annotated op DAG (a Program) — to P4.
  • tp/ep/pp shard-group coordinates on every macro, chip and op — to P5, which colors by them (D20).
  • Per-chip and per-macro occupancy, plus derived digital-pool sizing — to P4 and P5.
  • The per-boundary byte-rate table with named violations and disclosed relaxations — to P4 and P6.
  • The prefill/decode system pair and the priced handoff — to P4.
  • The (workload set, platform) → mapping policy seam — to future search work.
  • Stage-tagged validation failures in the DSE convention — to P6.

Open questions for George

  1. What is a chip? One macro per chip, or many macros per chip with the chiplet as the package unit? The relations work either way; the reports and P5's hierarchy read very differently.
  2. pp semantics. Is the chip chain the pp axis — chip index equals pipeline stage — or is pp an independent annotation over chips? This decides the schedule policy and P5's coloring.
  3. Shared digital chiplet count: a config input the user must get right, or derived-and-reported like the per-macro pool (D12)? Deriving it is more useful and slightly less honest.
  4. PD disaggregation: two physically separate inventories, or one inventory partitioned? The first is simpler and matches D16 literally; the second is what an edge box would actually do.
  5. Config surface: extend cim.chip, or open a new mapping: block? Extending keeps one config; a new block is honest that the concept has widened.
  6. Idle capacity: must every macro be fully owned, or are unowned columns legal and merely reported?
