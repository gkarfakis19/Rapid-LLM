Plan P5

The System Atlas

One self-contained page that draws a real mapping — package to chip to macro to tile, colored by parallelism group.

Mission context

The atlas is a deliverable, not a debug aid. It is the page George opens in front of people. It answers, in five seconds and without a caption, what the machine looks like and how the model sits on it.

It is also the mapper's honesty enforcer. The atlas draws objects, never quotients. A chip exists because it has an id and holds macros. A macro is drawn because it names its owners (D21). A mapping that cannot be drawn is not a mapping — OPTIMA's “layers/chip: 3” has no picture, because it is a division and not a placement (AUDIT finding 1).

The atlas computes nothing. Every number on screen arrives in the input file. That is deliberate: it is how the project avoids growing a second, disagreeing accounting inside a viewer (AUDIT finding 4, D21).

The encoding law

One fact, one channel. This is D21's “one accounting per metric” applied to pixels.

  • Hue is the parallelism group and nothing else (D20). Fixed hue order, assigned by group id, never cycled and never re-assigned when a filter changes what is visible.
  • Occupancy is a single-hue fill ramp, light to dark. Duty cycle is a separate small bar in the tile card. Neither ever becomes a hue, and no rainbow appears anywhere.
  • Outline is pool membership. Analog macro chiplet or shared digital chiplet (D13) — a border style, not a color.
  • Position is containment only. Grid order comes from ids, so the same file always draws the same picture and screenshots diff meaningfully.
  • Identity is never color alone. A legend is always on screen, and group membership is also printed in the card, so the figure survives grayscale print and color-vision deficiency.
  • Unknown is drawn, not inferred. A field the input omits renders as a hatch labeled unknown. The atlas never fills a gap with a guess.
  • The palette is checked with a CVD/contrast validator before the atlas ships; hue count stays small because the group axis is small.

What the loader refuses to draw

Renderer behavior, not process (D18). The atlas simply has nothing to put on screen when these fail, and says so in a validation panel.

  • A macro with no named owner set, or a tile whose macro or chip does not exist. Referential integrity is checked on load.
  • A fractional or derived chip count. If a producer emits chips as a quotient instead of a list, the loader names the field and stops.
  • Tile columns that exceed the macro's stored columns, or that overlap another tile's span.
  • Two unlabeled figures for one metric. Both are drawn only when both carry their own label and meaning (fabric ceiling vs sustained is the live example).
  • A non-empty relaxations[] renders as a persistent banner, never a footnote.

Machinery

  • One file. Inline JS, inline SVG, inline styles. It opens from a laptop with no network, from an email attachment, from a USB stick.
  • Data arrives two ways: a file input, or an embedded <script type="application/json"> blob so one file can be handed over with its mapping already inside.
  • SVG, not canvas. Nodes are countable, hit-testing is free, and the DOM is the debugger.
  • A stated draw budget for phase 1 (order 10k rects). Above it, only the opened chip is drawn. Say the limit out loud so the design does not quietly die on a large mapping.
  • Deterministic layout from ids. Same input, same picture, every time.

What a viewer learns in five seconds

  • Which macros are idle, and how much stored column the mapping wastes.
  • Where tp cuts, and whether an ep group straddles a chip boundary.
  • How much of the machine is analog and how much is shared digital — the finding D5 predicts for pure transformer LLMs.
  • Whether a bit-sliced weight composes inside one macro or chains across several (D11).
  • Whether the prefill system looks anything like the decode system (D16).

Seams

Imports

  • P3 — the mapping itself: tiles to macros, macros to chips, group indices, pool membership, PD systems, handoff and traffic-bearing links. The atlas renders it and derives none of it.
  • P4 — per-macro duty cycle, the labeled headline metrics, and the disclosed relaxations.
  • P2 — macro capacity semantics (stored columns = cols × mux), device-card identity, slice roles, the reported per-macro digital pool sizing (D12).
  • P1 — the owner vocabulary: model ids and layer / block / expert names the cards print.
  • P6 — the honesty invariants and their names, so the loader's refusals use the project's wording.

Exports

  • fws_atlas/1 — the mapping export contract. Frozen at phase 0, before renderer work, so P3 and P4 have one target.
  • A conformance check for free — any producer can run its output through the loader and learn whether its placement is real: integer chips, named owners, closed references, single accounting, disclosed relaxations.
  • The demo artifact — the atlas file itself, linked from the board.
  • A shared visual vocabulary — the tp / ep / pp hue order and legend, so every other figure in the project agrees with this one.

Open questions for George

  1. Separate atlas.json next to the mapping report, or an atlas block inside it? P5 proposes a separate file: one job, one schema, easy to hand someone.
  2. Which mapping is the fixture and therefore the demo? The Llama2-7B decode point at tp = 2 is the obvious first customer; a PD pair would exercise more of the schema at once.
  3. When a tile belongs to more than one group, which hue wins? P5 proposes P3 emits an explicit primary_group rather than the atlas inventing a precedence rule.
  4. Do the shared digital chiplets show op residency (which ops ran there), or only pool membership? Op residency needs P4's DAG and turns the chip view into a schedule.
  5. Is a single file with the data baked in a first-class output, or is file-drop enough for the demo?
