Plan P4

Evaluation

Price a mapped DAG analytically, then read every published number off one timeline.

Mission context

A1 removes the period law. The system builds the op DAG, prices each op on its assigned device, and evaluates the DAG. Latency, throughput and occupancy stop being formulas and become properties of the result.

That change buys one thing above all: honesty. AUDIT finding 4 caught OPTIMA carrying two TOPS accountings that disagreed by 10x inside one artifact. The defense is structural, not editorial. P4's rule is that every published number is a projection of a single simulated timeline. Two accountings of one metric cannot exist, because there is only one thing to read.

The evaluator is also the place where the far future stays cheap (D22). Fill and drain are visible in a DAG without being modeled. A latency-first, one-request-in-flight VLA regime is a different request mix on the same machinery, not a second evaluator.

Scope & exclusions

In scope: the pricing of a mapped DAG, the metric set, memory and energy accounting, the derived per-macro digital pool sizing, and the two reports (text section and machine-readable JSON).

Out of scope, by decision:

  • AstraSim. It is OFF for the QIF path (A1, D17). The Chakra emitter and the four AstraSim execution modes stay untouched and stay green for the GPU workloads; the FWS device layer is additive.
  • Congestion, topology and routing. Fully-connected p2p, analytical, no queueing (D17). Transfers are priced, never contended.
  • Mapping. P4 never chooses a placement. It prices the one it is given.
  • Laws. Every duration, energy and area number comes from the law layer (P2). P4 duplicates none of them.
  • Objectives, cost and area models (D19), accuracy (never a factor, D23), thermal.

The gap is precise. analytic_sim models one device kind with one outstanding compute per device. The QIF machine has three device kinds with different concurrency (A2), and resources that must not assume exclusive ownership (D22).

The investigation

One op, one device, one duration, one law source. The mapper (P3) states the assignment; P4 asks P2 for the number.

One subtlety worth naming now. P2's attention law carries an op-internal fill/drain term. The DAG carries a system-level ramp. They are different quantities with different names and are never summed into one "penalty" — one accounting per metric applies inside the pricing too.

3. Metrics as DAG properties

Serving semantics stay simple (D15): a batch of same-length requests, each prefilling S tokens and decoding N. Every number below is read off the one timeline. None is computed from a separate formula.

MetricRead from the timeline asReplaces
Prefill latencyFinish of the last op of the prefill subgraph, minus releaseThe closed form's block-latency arithmetic
Per-step decode timeFinish(step k terminal op) − finish(step k−1 terminal op); a series over k, reported with first / median / lastThe pipeline period as a per-token proxy
End-to-end request latencyFinish of the last decode op, minus release — measured once, not assembledend_to_end_latency = layers × block latency + endpoints + transfers
Steady throughputGenerated tokens (or completed requests) divided by the observed span of the same timelinefps = 1 / period; and the fabric-ceiling / sustained pair
Per-device occupancyBusy time / makespan per device, attributed to the named owner (tile, layer, expert, model)Per-chip occupancy as an array-count ratio
Macro duty cycleThe same projection restricted to analog macros — the P5 atlas colorant— (new)

The ceiling-versus-sustained pair deserves an explicit word. It existed because the closed form had no schedule: it could not tell whether the pipeline was actually full, so it printed a cap and a correction and named the limiting factor. The DAG knows. One throughput number is therefore the honest output, and KV or state capacity becomes a feasibility verdict (§5) rather than a term inside a throughput formula. This retires machinery; it adds none (D15). It also changes what the headline number means, so it is an open question below.

Two composition rules keep the far future cheap (D22). No metric may be defined as a period times a count — that reintroduces the steady-state assumption the DAG exists to remove. And latency composition stays additive over the actual critical path, so a one-request-in-flight regime reports a smaller number rather than needing a different definition.

4. The derived per-macro digital pool (D12)

The pool is sized so it never blocks the pipeline. P4 derives that size instead of assuming it: from the timeline, take each macro's peak concurrent digital demand — reduction trees, activations, elementwise — and report the width and area that make it non-blocking.

It is a reported diagnostic, not a constraint, and not a DSE axis for now. The honesty condition is that an absurd derived width is printed as an absurd derived width. Nothing is silently clamped, and no result is quietly relabeled feasible. If the sizing grows embarrassing, the report is where that becomes visible.

5. Memory accounting

Weights live in arrays, so weight bytes are not a memory question — they are an area and mapping question (P2, P3). What remains is feasibility:

  • Per-device high-water mark for activations, recurrent state, and KV, replayed over the same DAG.
  • Compared against the capacities declared by the device cards.
  • An overflow is a named violation with the offending device, owner and quantity — the DSE convention — and it is disclosed in the artifact, never absorbed (D21).

6. Energy accounting

One total, built from named components, each carrying its own coverage label. No aggregate figure exists that is not the sum of the printed parts, and efficiency figures are projections of that one total and the one throughput.

7. What survives of the closed-form report

It becomes a validation and legacy reference (A1). It is not deleted, and it is not published beside the DAG result — two accountings of one metric must never share an artifact.

The bridge is a real obligation: the degenerate case — one model, macros dedicated, no sharing, no contention — must reproduce the closed-form report. That comparison belongs to P6. P4's part is to export the DAG-side observables in the shape the comparison needs, and to keep the degenerate configuration expressible.

8. Reports

Two artifacts, one schema.

JSON blockWritten byRead by
Model and serving parametersP1 / configAll
Mapping: tiles, macros, chips, shard groups, owners, linksP3P4, P5
Evaluation: metrics, per-device occupancy and duty cycles, memory verdicts, energy components, derived pool sizingP4P5, P6, DSE
Disclosures: relaxations, approximations, coverage labelsWhoever relaxedP6

Schema rules: one version field; one producer per block; every metric names its accounting basis; no derived figure appears without the inputs it was derived from. The text results section is a rendering of the same blocks, never a second computation.

One open engineering point sits here. Pricing every decode step makes the DAG grow linearly in N. At the shapes in D15 that is comfortable; at long N it is not. The fallback is a step window plus a disclosed extrapolation — and under D21 the disclosure is part of the artifact, not a footnote.

Seams

Imports

  • P1 — the model set in scope and its serving parameters (S, N, B); the per-model op inventory the DAG must contain.
  • P2 — per-op duration, energy and area laws per device card; priced bit-slice reduction; per-macro pool component costs; macro occupancy semantics; device capacities for the feasibility check.
  • P3 — the mapped DAG itself: ops with device assignment and named owners, shard groups, transfer bytes, the PD handoff, and the device and link inventory.
  • P5 — the atlas's field requirements: which occupancy and owner fields must be named in the evaluation block for the visualization to color by shard group.
  • P6 — the validation stance (target vs provisional), the honesty invariants the reports must satisfy, and the definition of the closed-form bridge comparison.

Exports

  • The evaluator contract: a mapped DAG in, one timeline out (per-op start/finish, per-device busy intervals, owner attribution).
  • The metric set as DAG properties: prefill latency, per-step decode time, end-to-end request latency, steady throughput, per-device occupancy.
  • Per-macro duty cycles with named owners — the P5 atlas input.
  • The derived per-macro digital pool sizing, reported (D12).
  • Activation, state and KV feasibility verdicts with named violations — mapper feedback to P3.
  • Energy totals with per-component coverage labels.
  • The evaluation block of the shared report JSON, and the single-accounting report structure.
  • The degenerate dedicated-macro observables that the P6 closed-form bridge compares against.

Open questions for George

  1. The headline throughput. Tokens/s at the decode terminal, or requests/s from the batch makespan? And does the fabric-ceiling / sustained pair retire with the closed form, as §3 proposes, or must the DAG report keep printing both?
  2. Decode reporting shape. Per-step decode time as a full series, or first / median / last samples? The systolic staircase means sampling is an approximation, and long-N runs may need a step window with a disclosed extrapolation.
  3. Energy labels. Per-component coverage labels (the recommendation), or keep the single PARTIAL word the current report prints?
  4. Where the legacy report lives. A flag on run_perf, or reachable only from the validation script? The second is safer against a reader quoting the wrong number.
  5. Pool sizing threshold. Does the derived per-macro pool sizing get a loud warning above some fraction of macro area, or stay a pure report?
